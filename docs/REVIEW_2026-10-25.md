## Findings in the incoming changes

### R1 — P2: retain household requirements until the farmer changes them

Location: `src/components/planner-provider.tsx:68–70` and `src/domain/demo-planner.ts:386–394`.

Changing irrigation, soil, drainage or help availability invokes `settleHousehold`, which removes groups from the stored `farm.required` list to make a calendar possible. Changing weather/location can do the same. Reproduced in an isolated browser: a loam farm with reliable irrigation and required `[rice, potato]` became required `[rice]` immediately after selecting severe shortage. The UI does show “Potato was unticked…”, so the operation is not silent, but it has no confirmation and persists a different household requirement.

The form describes these groups as crops every option **must** include. An invented matching rule should expose the conflict rather than change that input automatically. Preserve the requirement and offer an explicit action to remove it; the crop page already has a deliberate household-removal action. This automatic behavior is intentional and tested in the update, but it changes the earlier requirements contract and should be a conscious product decision.

Evidence: `research/review-20261025/browser-review.json` (`beforeWater`, `afterWater`, `householdNotice`) and `household-auto-removal.png`.

### R2 — P2: identify the landing page as a mock concept

Location: `src/components/landing/landing-view.tsx:12–21` and its rendered page.

The new first page says “Know what to plant, every season” and “shows you why each one fits,” displays a fixed rotation under “Your field,” and shows coordinates. Its visible English page contains no prototype/mock-data notice. Bangla copy makes the same suitability promise. The planner still uses authored fixture values and unvalidated crop rules; NASA is not integrated. The previous mock/illustrative disclosures remain elsewhere, but the new entry page is outside the planner shell and does not show its illustrative-preview badge or data explanation.

Add a short bilingual concept/mock-data notice on this page and label the fixed field and rotation as illustrative. Keep suitability wording conditional on future validation. Existing planner warnings do not correct the standalone landing-page claim.

Evidence: `landing-desktop.png`, `landing-320.png` and the `landing` text in `browser-review.json`.

### R3 — P2: apply saved reading preferences on direct landing-page visits

Location: `src/app/(marketing)/page.tsx:8–11`; initialization currently depends on `ReadingControls` in the planner shell (`src/components/reading-controls.tsx:12–15`).

With a saved `ritu-display-v1` record selecting extra-large text and motion off, a direct `/` visit produced no `data-text-size` or `data-motion` attributes and a 20px root font. Visiting `/farm` in the same context applied `larger`/`off` and a 24px root font. The landing description also uses a fixed 19px size on desktop and 17px on phones, so merely initializing the store does not make that text follow the app's size preference.

Initialize display preferences in a shared root client boundary and use relative sizes for reading content on the landing page. Preserve the existing opt-in audio behavior; applying display settings should not start audio. The planner-only resizing and reflow tests pass, but they do not cover `/`.

### R4 — P2: make the sample-plan link show a sample

Location: `src/app/(marketing)/page.tsx:10–11`.

“See a sample plan” explicitly links to `/farm`, the same destination as “Plan my season.” Reproduced result: the farm-input heading appears and all journey flags remain null; no sample calendar is shown. For returning users, this also opens their existing farm, not a separate sample. The source comment acknowledges that the proposed example query is not implemented.

Either provide a read-only sample that preserves the user's stored data, or rename the link to describe opening the farm form. The missing sample does not break the normal guided planning flow.

## Other observations

- NASA integration remains absent. POWER and IMERG remain reference links; the implementation still uses mock environment/crop records. The update must not be described as adding real NASA data or scientifically validating crop suitability.
- The Google Fonts change introduces a network requirement when compiling uncached fonts. The application serves downloaded fonts locally afterward. An offline first build is no longer verified; retain a prepared build for an offline demonstration or self-host the new fonts.
- `@fontsource-variable/geist` and `@fontsource-variable/newsreader` remain declared even though the latest layout uses Google Anek Bangla/Hind Siliguri. These are cleanup candidates, not the cause of the successful build's runtime behavior.
- README still says `/` starts at the farm, lists 43/13 crops/rules rather than the actual 42/12, and describes a 20px/24px text contract that the new landing page does not fully follow. Some statements are inherited. Refresh current-state documentation separately from historical verification receipts.
- The palette and navigation are intentional redesigns: cream/off-white surfaces and light header replace the earlier white body/dark-green frame. They are design choices, not evidence of an eye-health or usability improvement.
